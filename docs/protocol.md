# 聊天通信协议

本文说明当前终端聊天室实际使用的换行文本协议，供阅读代码、手动联调和后续修改时参考。当前尚未采用包含消息类型和长度字段的二进制帧协议。

## 1. 连接与消息边界

- 传输方式：IPv4 TCP 长连接。
- 客户端启动：`./IMClient <IPv4地址> <端口>`。
- 每条请求以一个 LF 字节结束，即 C++ 字符 `\n`，十六进制值为 `0A`。
- 文本建议使用 UTF-8；服务端按字节处理，不校验聊天正文的编码。
- 服务端回复和转发也以 `\n` 结束，当前没有数值状态码、请求 ID 或长度字段。

本文代码块中的每一行代表一条以 LF 结束的消息；`/quit` 是客户端本地命令，例外见第 5 节。

### 1.1 TCP 接收不能直接当成消息

TCP 保留字节顺序，不保留应用层消息边界。例如发送：

```text
hello\nworld\n
```

一次 `recv()` 可能收到全部数据，也可能分别收到 `hel`、`lo\nwor` 和 `ld\n`。这里的 `\n` 表示实际的换行字节，不是反斜杠与字母 n。

服务端应将数据追加到对应连接的接收缓冲区，然后循环提取完整行。没有换行的尾部继续保留，等待后续数据。若直接连接服务器的其他程序在发送不完整行后关闭发送方向，这段残行会被丢弃，不作为消息处理。

### 1.2 空白与分隔规则

- 命令名区分大小写，只识别小写 `/name`、`/msg`。
- 命令与参数使用 ASCII 空格分隔，不自动将制表符转换为空格。
- 不自动去除行首、行尾空格。
- 不自动去除 CR 字节 `\r`；发送方应使用 LF，不要默认采用 CRLF。例如 `/name Alice\r\n` 中的 CR 会成为用户名的一部分并导致校验失败。
- 协议没有转义规则，正文中的换行会开始下一条请求，不能表达一条含内嵌换行的消息。

## 2. 连接状态与命名

连接状态流程：

```text
TCP 连接建立
    -> 未命名
    -> /name 校验成功
    -> 已命名，可发送群聊和私聊
    -> 连接关闭，清理 fd 和用户名索引
```

当前没有注册、密码校验或身份认证。用户名只是当前连接的临时名字；连接断开后，其他连接可以重新申请同名。fd 只用于服务器内部定位连接，不是稳定用户 ID。

### 2.1 设置用户名

请求：

```text
/name Alice
```

成功回复给请求者：

```text
用户名设置成功：Alice
```

用户名规则：

- 长度为 1–32 字节，只允许 ASCII 字母、数字和下划线。
- 区分大小写，`Alice` 与 `alice` 可以同时存在。
- 在线用户名不能重复。
- 每个连接只能成功命名一次，不能用 `/name` 改名。
- 命名失败不关闭正常连接，可以重新输入。
- `/name ` 后的全部内容均作为用户名，因此额外空格也会参与校验。

当前回复：

| 场景 | 回复正文 |
| --- | --- |
| 单独输入 `/name` | `用户名不能为空` |
| `/name ` 后为空，或用户名超过 32 字节 | `用户名长度不对` |
| 包含空格、中文或其他非法字符 | `用户名字符非法` |
| 用户名被其他在线连接占用 | `用户名已经被占用` |
| 已命名连接再次执行带参数的 `/name` | `当前连接已设置用户名` |

表中回复正文在网络上传输时均带末尾 LF。单独的 `/name` 在当前解析顺序下始终先返回“用户名不能为空”。

### 2.2 未命名时的限制

未命名连接发送普通文本、空行、`/msg` 或其他非 `/name` 请求时，回复：

```text
请先设置用户名
```

这些输入不会被当成聊天内容转发。当前广播接收列表仍包含所有其他在线连接，包括未命名连接；临时命名不是消息访问控制。

## 3. 群聊

已命名的 Alice 输入普通文本：

```text
hello world
```

其他在线客户端收到：

```text
[Alice]:hello world
```

- Alice 不收到自己的群聊广播，也没有单独的群聊成功回复。
- 正文中的空格保留，冒号后没有自动插入空格。
- 已命名连接发送空行有效，其他客户端收到 `[Alice]:` 加换行。
- 以 `/` 开头的完整行进入命令解析，不能直接作为普通群聊发送。
- 不同客户端同时发送时，由事件循环决定处理顺序，协议没有跨客户端的时间顺序保证。

## 4. 私聊

请求格式：

```text
/msg Bob hello there
```

假设发送者为 Alice，只有 Bob 收到正文：

```text
[private Alice]:hello there
```

Alice 收到：

```text
私聊消息已入队
```

Carol 等其他连接不收到这条私聊，也不收到 Alice 的成功提示。

### 4.1 参数解析

`/msg ` 后，以第一个 ASCII 空格分开目标用户名和正文。目标与正文都必须非空，不会去除正文的额外空格。

例如 `/msg Bob hello  there ` 会保留正文中的两个连续空格和末尾空格。当前实现只判断正文是否为空字符串，不额外拒绝完全由空格组成的正文。

### 4.2 错误回复

| 场景 | 回复正文 |
| --- | --- |
| 单独输入 `/msg` | `发送信息不能为空` |
| `/msg ` 后没有分隔目标与正文的空格 | `私聊格式错误，正确格式：/msg 用户名 消息` |
| 目标或正文为空 | `私聊格式错误：用户名或消息不能为空` |
| 目标是发送者自己 | `不能给自己发送私聊` |
| 目标用户名不在线 | `用户不在线` |
| 目标连接消息入队失败 | `私聊发送失败：目标连接不可用` |

以上为正常错误回复路径。如果请求者自己的回复队列也无法入队，则直接清理请求者连接，不能保证它收到错误文字。

### 4.3 入队与送达的区别

“私聊消息已入队”表示服务端已经将消息放入目标连接的用户态发送队列，并成功启用可写事件关注。它不代表数据已经发送完毕，更不代表目标客户端已接收、显示或阅读。

目标可能在入队后断开，因此仍有消息未送达的可能。当前不提供消息 ID、送达确认、重试去重、离线投递或历史记录。

## 5. 退出与未知命令

### 5.1 `/quit`

`/quit` 由 `IMClient` 本地识别，正常返回 `0`，通过 RAII 关闭 socket。该行及其后已经读入但未处理的输入不会发送给服务器。

只有精确的 `/quit` 行会触发退出；附带空格或其他参数的文本不是该本地命令。标准输入 EOF 时，剩余内容恰好是 `/quit` 也会本地退出。

服务端没有实现 `/quit` 命令。其他 TCP 程序若直接发送 `/quit\n`，未命名时得到命名提示，已命名时得到未知命令提示。

### 5.2 标准输入 EOF

`IMClient` 读取标准输入返回 `0` 时：

1. 若存在非空残行，补 LF 并发送；残行为 `/quit` 则本地退出。
2. 关闭连接并正常退出，不等待所有服务器回复或聊天消息显示完毕。

因此管道发送者输入结束后，可能来不及显示命名或私聊入队回复。验证广播时应使用另一个保持连接的客户端观察。

### 5.3 未知命令

已命名连接发送其他以 `/` 开头的行，例如 `/help`、`/NAME Alice` 或 `/msgBob hi`，回复 `未知命令\n`。当前没有 `/help`、`/ping`、`/pong` 或登录命令；心跳将在后续阶段加入。

## 6. 长度与资源限制

### 6.1 单行输入

单行长度上限为 `64 * 1024 = 65536` 字节，不包含末尾 LF，命令名、分隔空格和参数全部计入。

| 输入 | 结果 |
| --- | --- |
| 65536 字节正文加 LF | 长度合法 |
| 65537 字节正文加 LF | 超限 |
| 不含 LF 的残行累计超过 65536 字节 | 超限，不继续等待换行 |
| 多条合法行合计超过 65536 字节 | 逐行处理，不能仅因总量超限而拒绝 |

这里的“长度合法”不代表命令或命名状态一定合法。`std::string::size()` 统计字节数，UTF-8 中文字符可能占多个字节。

例如 `/msg Bob ` 前缀占 9 字节，正文还需与前缀共同满足单行上限。服务端转发时会增加用户名格式前缀，因此输出行可能比输入行更长；客户端接收显示不能把输入的 64 KiB 上限直接套用到输出行上。

当前服务端已实现该检查，超限时向服务端标准错误输出 `Message too long` 并清理连接，不保证给客户端发送错误回复。客户端主动限制输入长度仍待本阶段补齐；完成前，超长输入可能先发送到服务端并被断开。

客户端补齐时，完整行按 LF 位置判断，提取完整行后再检查剩余残行；标准输入 EOF 时，也应检查残行长度，再补 LF。客户端拒绝超长输入时应打印错误并返回 `1`。

### 6.2 待发送数据

每个连接的未发送数据上限为 `1024 * 1024 = 1048576` 字节，计算方式：

```text
pending = output.size() - sent
```

新入队数据与 `pending` 之和超过上限时，拒绝入队，由调用方清理相应连接。限制包含转发前缀、正文、回复文字和换行，不是消息条数限制，也不是整个进程或内核 socket 缓冲的内存上限。

发送过程处理部分发送，遇到 `EAGAIN` 保留未发送部分，等待下一次 `EPOLLOUT`。队列发完后取消可写关注，避免空闲忙循环。入队或发送失败会导致目标连接清理；群聊可对部分接收者成功、对其他接收者失败，没有整体成功回复。

## 7. 断开与清理

- `recv() > 0`：处理收到的字节；不是一条消息长度的保证。
- `recv() == 0`：对端有序关闭发送方向，当前实现清理整个连接，不保留只发送不接收的半连接状态。
- `EINTR`：重试系统调用。
- 非阻塞 `recv()` 返回 `EAGAIN` 或 `EWOULDBLOCK`：当前无数据可读，保留连接并返回事件循环。
- 不可恢复的接收、发送或事件更新错误：清理对应连接。

收到数据后紧接着收到 EOF，已提取的完整行仍会进入命令或聊天处理；尚无 LF 的尾部丢弃。连接清理会删除用户名索引、取消 epoll 关注并销毁连接的 `Socket`，其未发送队列也会丢弃，不再保证回复送达。

## 8. 最小手动联调

1. 启动服务器，并连接 Alice、Bob、Carol 三个客户端。
2. 命名前发送普通文本，确认收到命名提示。
3. 分别执行 `/name Alice`、`/name Bob`、`/name Carol`。
4. Alice 发送群聊，确认 Bob、Carol 收到，Alice 不收到广播。
5. Alice 执行 `/msg Bob hello  there`，确认 Bob 收到保留空格的正文，Alice 收到入队提示，Carol 无私聊内容。
6. 验证重复用户名、非法用户名、离线目标、自发私聊和缺失参数。
7. Bob 输入 `/quit` 后，由新连接重新命名为 Bob，确认新私聊到达新连接。
8. 用测试程序验证分段行、多行、空行、64 KiB 边界、超长残行和 EOF 尾部。

客户端超长输入拒绝属于待完成项，不能仅依据本文目标判定已经实现。当前 CTest 的日志检查也不能替代接收者实际收到消息的验证。
